# Инстансы

Команды управления инстансами - `tt instance start`, `stop`, `restart`,
`kill`, `status`, `logs`, `logrotate`, `check`, `clean` и `connect` -
работают с инстансами приложения на этом хосте. `tt connect` - это
`tt instance connect`, а `tt play` принимает те же цели.

## Пара файлов {#the-pair}

Приложение запускается по паре файлов:

- `instances.yaml`, описание: что именно работает на этом хосте;
- `config.yaml`, кластерная конфигурация, с которой запускается Tarantool 3
  (`tarantool -c`).

Пара берётся целиком из одного каталога:

- **шаблон** приложения, `.templates/<name>/`: `default`, если в
  `--template` не указан другой. Проект всегда работает по шаблону, как и
  установленное приложение, у которого нет пары хоста.
- **пара хоста**, `<root>/etc/<app>/`, для приложения, установленного в
  пользовательский или системный scope. Если она есть, она имеет преимущество
  над шаблонами и лежит отдельно от установленной версии, поэтому сохраняется
  при обновлении. При наличии пары хоста флаг `--template` отвергается.

Повреждённая пара считается ошибкой и никогда не служит поводом откатиться
на другую.

## Описание {#the-description}

`instances.yaml` сопоставляет имена инстансов с записями:

```yaml
storage-001:
storage-002:
  restart: on-failure
gateway:
  binary: ./bin/gateway
legacy:
  script: init.lua
```

Запись бывает трёх видов:

- **Инстанс Tarantool, настроенный кластерной конфигурацией**: запись без
  `binary` и `script`, например `storage-001`. Она должна входить в топологию
  `config.yaml`; в топологии могут быть и другие инстансы, работающие на
  других хостах.
- **Инстанс Tarantool со своим собственным скриптом**: запись со `script`,
  настраиваемая через `box.cfg` в скрипте, как работали приложения tt 2.x.
  См. [Run a box.cfg application](../how-to/script-instances.md).
- **Внешний процесс**: запись с `binary` - программа не на Tarantool,
  которая запускается, останавливается и показывается рядом с инстансами
  Tarantool. См. [Run an external process](../how-to/external-processes.md).

Запись `"*"`, в кавычках, обозначает каждый инстанс топологии `config.yaml`,
не названный другими записями; каждый такой инстанс - это инстанс Tarantool
с полями из `"*"`. Собственная запись заменяет `"*"` для своего инстанса
целиком. Инстансы, которые задаёт `"*"`, запускаются по порядку своих имён.

Шаблон, состоящий только из `config.yaml`, запускает всю свою топологию точно
так же, как запись `"*": {}`. Паре хоста описание необходимо: оно указывает,
что именно работает на этом хосте, тогда как остальная часть кластера может
работать на других.

Описанию, состоящему только из инстансов со скриптами и внешних процессов,
`config.yaml` не нужен. Файл `config.yaml`, содержащий лишь `config.etcd` или
`config.storage`, подтягивает остальную кластерную конфигурацию из этого
хранилища.

Все поля описаны в [справочнике](../reference/instances-yaml.md).

## Цели {#targets}

Команды управления инстансами принимают цели:

- `<app>:<instance>`, `<app>:*` или их список через запятую;
- без цели: все инстансы текущего проекта.

`<app>` - это текущий проект, если он назван так же, а иначе - приложение,
установленное в системный scope. Флаг `--scope project|user|system` выбирает
scope напрямую, и в пользовательский scope попадают только так. Имя `<app>`
без указания инстанса отвергается: забытое имя инстанса не должно
останавливать все инстансы сразу.

```console
$ tt instance start                               # все инстансы проекта
$ tt instance start myapp:storage-001 --scope user
$ tt instance stop myapp:* --yes
$ tt instance logs myapp:storage-001 --follow
```

## Запуск {#running}

`tt instance start` запускает каждый инстанс в фоне под watchdog'ом tt.
Watchdog перезапускает инстанс после его самостоятельного выхода, если это
предписано полем `restart`: `no` (по умолчанию), `on-failure` или `always`.

С флагом `--foreground` tt вместо этого остаётся на переднем плане: для
systemd, контейнера или терминала. Каждый инстанс по-прежнему работает под
собственным watchdog'ом, который его не перезапускает, поэтому команды
`tt instance stop`, `kill`, `logrotate` и `status` работают с ним из
другого терминала. Вывод инстансов поступает в их логи и в стандартный
вывод tt с префиксом имени инстанса, когда их несколько. Сигналы SIGINT,
SIGTERM и SIGQUIT, отправленные tt, останавливают каждый инстанс. tt
завершает работу, когда завершились все они: с кодом 0, если они успели
вовремя остановиться; с кодом 137, если какой-то инстанс не уложился в свой
`stop_timeout` и был принудительно завершён; в остальных случаях - с кодом
первого инстанса, завершившегося с отличным кодом.

Остановка посылает инстансу его сигнал `stop_signal`, по умолчанию SIGTERM, и
принудительно завершает его по истечении `stop_timeout`, по умолчанию
30 секунд.

Инстансы запускаются по порядку из описания, и ни один не ждёт готовности
другого. Попытка запустить уже работающий инстанс - ошибка ещё до того, как
начнётся запуск остальных.

## Где находятся файлы {#where-the-files-go}

Инстанс приложения `<app>` хранит свои файлы под корнем scope'а этого
приложения:

| Каталог | Содержимое |
| --- | --- |
| `<root>/var/lib/<app>/<instance>/` | данные: `*.snap`, `*.xlog`, vinyl; рабочий каталог внешнего процесса |
| `<root>/var/log/<app>/<instance>/` | `tt.log`: вывод инстанса и его watchdog'а |
| `<root>/var/run/<app>/<instance>/` | `tt.pid` watchdog'а, `tarantool.pid`, сокет консоли `tarantool.control`; `process.pid` внешнего процесса |

В проекте `<root>` - это `.tarantool/`. Инстанс Tarantool работает в каталоге
приложения: в проекте либо в установленной версии. tt передаёт ему эти пути
через переменные окружения `TT_*_DEFAULT`, поэтому кластерная конфигурация
может указывать другие пути.

`tt instance clean` удаляет данные и лог неработающих инстансов.

## Подтверждения и коды возврата {#confirmations-and-exit-codes}

`stop`, `restart`, `kill` и `clean` запрашивают подтверждение, которое флаг
`--yes` (`-y`) пропускает. Подтверждение запрашивается только в терминале: в
скрипте или пайпе команда, требующая подтверждения, завершается с кодом 1,
если ей не передан флаг `--yes`.

Если команда действует на несколько инстансов, она продолжает работу,
когда один из них сбоит. Она завершается с кодом 3, если сбой произошёл лишь для части
инстансов; с кодом 1, если сбой произошёл для всех инстансов; и с кодом
самой ошибки, если инстанс был только один. См.
[Exit codes](../reference/commands/errors.md).

## Под systemd {#under-systemd}

`tt service systemd` создаёт юниты systemd, которые запускают инстансы
приложения системного scope'а; после этого команды управления инстансами
отказываются запускать или останавливать эти инстансы в обход юнитов. См.
[Run instances under systemd](../how-to/systemd.md).
