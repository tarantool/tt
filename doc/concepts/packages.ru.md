# Пакеты

Пакет  -  это приложение, описанное в `app.manifest.toml`: его имя, версии
Tarantool и tt, на которых оно работает, его зависимости, компоненты, из
которых оно собирается, и продукты, в виде которых оно упаковывается. Пакет
разрабатывается в [проекте](projects-and-scopes.md), упаковывается в архив
и устанавливается из него.

## Манифест {#the-manifest}

```toml
manifest_version = "0.1"

[package]
name = "kv-api"

[platform]
tarantool = ">=3.0.0"          # по умолчанию [ce]; ">=3.3.0[ee]" для Enterprise
tt = ">=3.0.0"

[dependencies]
checks = ">=3.0.0"             # rock-модуль с rock-серверов
mylib = { source = "path", path = "../mylib" }

[dev_dependencies]
luatest = "*"

[components.app]
path = "kv"
```

`tt new` создаёт каркас манифеста; `tt package add` и `tt package remove`
редактируют секцию `[dependencies]` на месте, сохраняя комментарии и
порядок. Неизвестное поле считается ошибкой, поэтому опечатка не останется
незамеченной. Описание всех полей приведено в
[справочнике](../reference/app-manifest.md).

## Локфайл {#the-lock}

`app.manifest.lock` рядом с манифестом фиксирует точные версии всех
зависимостей, прямых и транзитивных. Его стоит коммитить: сборка одного и
того же коммита везде установит одни и те же версии. Для rock'а с
сервера с [rock-индексом](rock-servers.md#a-rock-index) он
фиксирует ещё и sha256 файлов версии, а установка проверяет по нему файл
своей платформы.

Локфайл меняется только по запросу:

- `tt package add`, `tt package remove` и `tt package resolve` заново
  разрешают локфайл под то, что объявлено в манифесте, сохраняя все версии,
  уже зафиксированные в локфайле. Измениться могут только добавленная
  зависимость и то, что требуется ей.
- `tt package update [NAME]` берёт самые новые версии, разрешённые
  ограничениями, для всех зависимостей или только для NAME.
- `tt package build` и `tt package pack` разрешают локфайл, переставший
  соответствовать манифесту, сохраняя зафиксированные версии. С флагом
  `--locked` они вместо этого завершаются с ошибкой, как и нужно в CI.

Версия, которая следует за веткой, `scm-1` или `dev-1`, выбирается, только
если её называет ограничение или других версий у rock'а нет, а
разрешение на неё предупреждает, что локфайл не зафиксирует неизменный код.
Так же и с версией, которую tt сделал из незакоммиченных изменений,
`1.2.0.dirty-1`: её получает любая такая сборка коммита. Версия, которую tt
делает из коммита, `1.2.1.dev.3.gabc1234-1` или `0.0.0.dev.36.g7170ebf-1`,
называет этот коммит и считается релизом.

Локфайл связан с манифестом через `manifest_hash`  -  хеш того, что
говорит манифест (его таблиц, ключей и значений), а не байтов файла.
Комментарии, пустые строки и отступы, порядок ключей и таблиц, кавычки
строк и форма таблицы (встроенная, ключи через точку) не учитываются, так
что после такой правки локфайл остаётся актуальным. Изменённый ключ или
значение делает локфайл устаревшим, даже если от него ничего не
зависит, как от `description`; устаревшим считается и локфайл, записанный
версией tt, которая хешировала манифест иначе. Тогда
`tt package resolve` записывает хеш заново и, если ни одна версия не
изменилась, сообщает, что именно переписал в локфайле, а не что он
актуален.

`tt package deps` показывает, что объявлено в манифесте и во что это
разрешил локфайл, без обращения к сети.

Зависимости загружаются с rock-серверов; см.
[Rock-серверы](rock-servers.md).

## Компоненты и продукты {#components-and-products}

Компонент  -  это часть пакета: каталог с файлами и, при необходимости,
правилами сборки.

- Компонент-**модуль** (по умолчанию) раскладывает свои файлы по пути
  `.rocks/share/tarantool/<namespace>/`, где `<namespace>`  -  имя пакета,
  если в компоненте не указано иное. Его файлами считаются `*.lua` и `*.so`
  из его каталога `path`, если только в `include` не перечислены другие.
  Бэкенд сборки  -  `c`, `lua-c`, `cargo`, `cmake`, `make` или `shell`  -
  сначала собирает нативный модуль или WebAssembly-компонент: см.
  [Run WebAssembly components](../how-to/wasm-components.md). Бэкенд
  `cargo` описан в [Build a module in Rust](../how-to/rust-modules.md).
- **Исполняемый** компонент, `kind = "executable"`, собирает программу в
  `.rocks/bin/` с помощью бэкенда `go`, `cargo`, `cmake`, `make` или
  `shell`. Её запускает [внешний процесс](../how-to/external-processes.md)
  приложения.

Нативный модуль кладётся как `<module>.so` в
`.rocks/lib/tarantool/<namespace>/`, а на macOS  -  как `<module>.dylib`, где
Tarantool не ищет файл с другим именем: бэкенды `c`, `lua-c` и `cargo` так его
и называют, `cmake` копирует туда собранный `.so` как `.dylib`, а файл
`.dylib`, разложенный компонентом, попадает туда так же, как и `.so`.

Продукт  -  это набор компонентов, собираемых и упаковываемых вместе.
Манифест без `[products]` содержит один неявный продукт, `default`,
состоящий из всех компонентов.

## Сборка {#building}

`tt package build` разрешает локфайл, устанавливает зависимости в `.rocks/`,
запускает бэкенды сборки компонентов и раскладывает компоненты по каталогам
вместе с `version.lua` пакета. `tt package fetch` только устанавливает
`.rocks/` по локфайлу, без сборки.

Компоненты раскладываются в `_build/rock/<product>/` и устанавливаются оттуда
в `.rocks/` как rock пакета. Этот каталог сохраняется между сборками, а
`_build/rock/<product>.json` записывает, какой компонент положил туда каждый
файл. Сборка удаляет из него, а значит и из `.rocks/`, то, что больше не
принадлежит ни одному компоненту: файл, удалённый из исходников, файлы
компонента, исключённого из продукта. То, что записала пропущенная
инкрементальная сборка, остаётся, как и файлы других компонентов при сборке
одного компонента через `--component`. Файл, однажды записанный бэкендом в
`TT_OUTPUT_DIR` и с тех пор не тронутый, остаётся за ним, как цель `make`, не
требующая пересборки; `--rebuild` начинает с пустого
`_build/rock/<product>/`, и остаётся только то, что сборка запишет заново.

- Бэкенд сборки находит программы из `.tarantool/bin` проекта  -  то, что
  установили `tt binary` и `tt wasm prepare`,  -  впереди `PATH`, с
  `.env/activate.sh` или без него.
- Сборка `make` или `shell` с `incremental = true` пропускается, пока ни
  одна из её зависимостей не изменилась; см.
  [Инкрементальная сборка](#incremental-builds).
- Файл `.wasm`, раскладываемый компонентом, обязан быть бинарным файлом
  WebAssembly: любой другой приводит к ошибке сборки, а core-модуль,
  который tarantool-wasm не загружает, раскладывается с предупреждением.
- `tt package build`, `fetch` и `pack` не требуют Tarantool: если tt не
  находит его ни в `.tarantool/bin`, ни в `PATH`, пакет на Lua всё равно
  собирается и упаковывается. Тогда с ошибкой, которая говорит об этом,
  завершается то, что компилируется с заголовочными файлами Tarantool:
  компонент `c` или `lua-c` - ещё до начала сборки, и rock сервера с
  частью на C. Сборке `make`, `shell` или `cmake` не сообщается, где
  Tarantool: `TT_TARANTOOL_PREFIX` и `TT_TARANTOOL_INCLUDE_DIR` не заданы, и
  если ей нужны заголовочные файлы, она завершается с собственной ошибкой.

Версия пакета определяется по порядку:

1. строка файла `VERSION` рядом с манифестом;
2. ближайший git-тег версии, `v1.2.0` или `1.2.0`: `1.2.0` на самом теге,
   `1.2.1-dev.3+gabc1234` через три коммита после него;
3. `0.0.0-dev.<N>+g<sha>`, если тегов нет.

Тег с `v` - версия, как и раньше, `v1.2` тоже; тег без `v` - только полная
SemVer, `1.2.0` или `1.2.0-rc.1`, потому что голое число так же часто
обозначает дату или номер сборки. Любой другой тег пропускается, и берётся
тег версии перед ним. Из тегов версий на одном коммите в счёт идёт
наибольшая версия, а из `v1.2.0` и `1.2.0` тегом считается `v1.2.0`,
какой бы из них ни был аннотированным или более новым.

Незакоммиченные изменения, кроме изменений локфайла, добавляют `dirty` в
метаданные сборки: `1.2.0+dirty`.

Проект в подкаталоге своего репозитория - один из проектов монорепозитория
или path-зависимость внутри репозитория проекта, который от неё зависит, -
получает версию только по своему каталогу. Версия берётся от последнего
коммита, менявшего каталог, и `dirty` добавляют только изменения внутри
него: коммит или изменение в другом месте репозитория не сдвигает версию и
не делает устаревшим локфайл проекта, который зависит от этого проекта по
пути. Тег учитывается на этом коммите или до него, но не на более позднем
коммите, который каталог не трогал: чтобы выпустить такой проект, ставьте
тег на коммит, который его меняет. `<N>` - число коммитов в истории этого
коммита, включая коммиты в других местах, так же как считаются коммиты
после тега. Проект в корне репозитория получает версию по `HEAD` и всему
дереву.

Код считывает свою версию через `require('<name>.version').version`;
укажите `generate_version_lua = false` в секции `[package]`, чтобы не
создавать `version.lua`.

### Инкрементальная сборка {#incremental-builds}

Сборку компонента через `make` или `shell`, будь то модуль или исполняемый
компонент, можно пропускать, когда ничего из того, от чего она зависит, не
изменилось с прошлой сборки:

```toml
[components.calc.build]
backend = "shell"
command = "tarawasm"
args = ["all"]
incremental = true
```

Перед сборкой такого компонента `tt package build` хеширует его входные
данные:

- его блок сборки, включая `env`, `cwd`, `output` и всё остальное;
- файлы в его каталоге `path`: каждый обычный файл  -  по правам доступа и
  содержимому, а каждую символическую ссылку  -  по тому, куда она указывает.

Некоторые файлы не считаются входными данными:

- скрытые файлы на любой глубине: `.git`, `.tarawasm`, сами файлы
  `.gitignore`;
- файлы в каталогах `_build/` и `_runtime/`;
- файлы, которые игнорируются файлами `.gitignore`: проектом, каталогами по
  пути к компоненту и самим компонентом, каждый для своего поддерева, как их
  читает git, но без правил игнорирования из конфигурации git
  (`core.excludesFile`, `.git/info/exclude`).

То, что сборка записывает и что git не отслеживает  -  её результат, файлы
привязок (bindings),  -  не попадает во входные данные, и хеш остаётся
неизменным от сборки к сборке.

Сборка пропускается, когда хеш совпадает с сохранённым при прошлой успешной
сборке в `_build/cache/<component>.json`, а то, что оставила та сборка, всё
ещё на месте:

- файлы из списка `output`;
- файлы компонента, перенесённые раскладкой;
- файлы, записанные в `TT_OUTPUT_DIR` на любой глубине: созданные или
  изменённые ею, а также созданные более ранней сборкой и оставленные без
  изменений, как делает цель `make`, не требующая пересборки. У исполняемого
  компонента это его программы.

Сборка, писавшая в `.rocks/`, который с тех пор был очищен, запустится
снова. Пропущенная сборка повторно копирует файлы из списка `output` в
`.rocks/`, и компонент раскладывается так же, как после обычной сборки.
`tt -V package build` выводит в лог каждый пропущенный компонент.

При пропуске сборки её бэкенд вообще не запускается. Цель `make` с
собственными правилами отрабатывает дёшево, когда ничего не изменилось, и
может обойтись без `incremental`: без него tt запускает make каждый раз, а
make сам решает, что пересобирать.

Хеш учитывает не всё, от чего зависит сборка:

- компиляторы и их версии;
- окружение, в котором работает tt, за исключением `env` из блока сборки;
- файлы за пределами каталога `path` компонента, включая файлы из другого
  `cwd`;
- зависимости в `.rocks/`.

После их изменения `tt package build --rebuild` и
`tt package pack --rebuild` пересобирают каждый инкрементальный компонент и
сохраняют хеш; удаление `_build/cache/` даёт тот же эффект.

Компонент, сборка которого создаёт файлы, не игнорируемые ни одним
`.gitignore`, получает новый хеш при каждой сборке и собирается каждый раз,
как если бы он не был инкрементальным. `tt wasm new` создаёт `.gitignore` для
WebAssembly-компонента и объявляет его инкрементальным.

## Упаковка {#packing}

`tt package pack` собирает пакет и упаковывает его в архив tar.zst
`_build/pack/<name>-<version>-<os>-<arch>.tt`, выводя путь к нему. Архив
воспроизводим: упаковка одного и того же коммита дважды даёт одинаковые
байты. В него входят:

- манифест, локфайл и `VERSION`;
- `.rocks/`: компоненты и зависимости, за исключением dev-зависимостей;
- `.templates/`: шаблоны инстансов проекта, каждый проверен;
- `_runtime/`: Tarantool и tt, на которых работает пакет, а также TCM, если он
  запрошен в `[platform].tcm`;
- файлы из списка `[package].include` и файлы лицензий.

Другие файлы проекта, например `init.lua` в его корне, в архив не попадают,
если только они не указаны в `[package].include`. Поэтому кластерная
конфигурация пакета загружает его код как `app.module: <name>`, из `.rocks/`.

Каждый runtime  -  это первый из следующих вариантов, который соответствует
`[platform]`:

1. наибольшая версия в кеше runtime,
   `~/.cache/tt/runtimes/<tarantool|tt|tcm>/<ce|ee>/<version>/`
   (`$XDG_CACHE_HOME/tt/runtimes/`, если переменная задана;
   `~/Library/Caches/tt/runtimes/` на macOS). Ни одна команда его не
   наполняет: в нём хранятся сборки, помещённые туда вручную, каталог с
   `bin/<name>` и, для Tarantool, его `LICENSE` и `include/tarantool/`;
2. установка пакетом tt binary в проекте, в `.tarantool/versions/`:
   активная, которую выбирают `tt binary install` и `tt binary switch`,
   а иначе  -  наибольшая версия. Таким образом, команда
   `tt binary install tarantool 3.8.1` в проекте или `tt binary install tt`
   выбирает, что именно упакует pack. Требование `[ee]` берёт `tarantool-ee`
   и `tt-ee`; SDK или сборка, названная по коммиту, не берутся. Заголовочные
   файлы tarantool идут вместе с ним, а локфайл фиксирует имя установки;
3. активные `tarantool` и `tt`, с предупреждением.

Если `tarantool` не найден, первые два варианта остаются единственными его
источниками, и упаковка завершается ошибкой, когда подходящей сборки нет ни в
одном из них. tt binary устанавливает tarantool без его файла лицензии,
поэтому pack предупреждает, что упаковывает сборку из установки без лицензии.

Флаг `--without-deps` упаковывает только сам пакет: без
`_runtime/` и без зависимостей, которые `tt package install` скачивает по
локфайлу. Такой архив называется `...-any.tt`, если в нём нет нативных
файлов.

### Упаковка в rock {#packing-a-rock}

Пакет, от которого зависят другие проекты, например модуль Tarantool,
упаковывается в rock: `tt package pack --format rock`. В rock'е лежат файлы,
которые разложила сборка, - это тот же rock пакета, который
`tt package build` ставит в `.rocks/`, - и файлы лицензии,
`[package].license_files`, в `doc/`, где LuaRocks хранит документы rock'а:
у проекта, который ставит rock, они оказываются в
`.rocks/share/tarantool/rocks/<name>/<version>/doc/`. Рядом с rock'ом
записывается его rockspec:

```console
$ tt package pack --format rock --out dist
.../mylib/dist/mylib-1.2.0-1.linux-x86_64.rock
.../mylib/dist/mylib-1.2.0-1.rockspec
```

Если в пакете есть нативный файл (модуль или программа), получается
бинарный rock той платформы, на которой работает tt, а иначе -
`<name>-<version>.all.rock`. Нативный файл, собранный под другую
платформу, проваливает упаковку. Версия rock'а - версия пакета с ревизией из
`--revision`, по умолчанию 1: её поднимают, чтобы опубликовать новую сборку
уже вышедшей версии.

Rockspec в проекте не нужен: tt делает его из манифеста. Зависимости в нём  -
это диапазоны, которые объявляют `[dependencies]` и компоненты продукта, а
не версии, зафиксированные в локфайле, а `[platform].tarantool` становится
его зависимостью от `tarantool`; источник  -  это `[package].repository` на
коммите версии: `source.tag`  -  это тег версии под тем именем, что у него в
git, а для версии коммита, которую не называет ни один тег (например,
`1.2.1-dev.3+gabc1234`),  -  полный sha коммита, поскольку у LuaRocks нет
поля для коммита. LuaRocks скачивает git-источник через `git clone --branch`,
который не принимает коммит, поэтому он завершается ошибкой при попытке
скачать источник такого rockspec, вместо того чтобы скачать другой коммит; tt
не скачивает источник ни одного rock. Версия `dirty` с незакоммиченными
изменениями и версия из файла `VERSION` называют репозиторий без коммита,
причём версия `dirty`  -  с комментарием, который сообщает об этом; пакет без
`repository` получает источник `file://.`.
Описание, лицензию и сопровождающих даёт
`[package]`, поддерживаемые платформы -
`[platform].platforms`. Сборка уже сделана, поэтому тип сборки `none`, и
rockspec одинаков у rock'а любой платформы. Path-зависимость проваливает
упаковку: у проектов, которые ставят rock, такого каталога нет. Так же её
проваливает продукт без своего rock'а, и оба случая - до сборки, а не после
минут её работы. Зависимость со своим реестром объявляется с
предупреждением, потому что rockspec не может назвать сервер.

Каталог `--out`, по умолчанию `_build/pack/`, после записи rock
индексируется как rock-сервер, с сохранением уже находящихся там rock:
упаковка на каждой платформе в один каталог наполняет один сервер. Каталог
получает манифесты LuaRocks и [rock-индекс](rock-servers.md#a-rock-index),
`tt-rocks-index.json`, построенные по каждому rock и rockspec в нём:

```console
$ ls dist
manifest
manifest-5.1
manifest-5.2
manifest-5.3
manifest-5.4
mylib-1.2.0-1.linux-x86_64.rock
mylib-1.2.0-1.rockspec
tt-rocks-index.json
```

Другой проект затем зависит от rock из него, а его локфайл фиксирует sha256
каждого файла версии, перечисленного в индексе, что проверяет каждая
установка этого rock:

```toml
[dependencies]
mylib = { version = ">=1.2.0", registry = "/path/to/dist" }
```

Rock, упакованный заново с той же версией, но другими байтами, больше не
соответствует такому локфайлу: `tt package resolve` фиксирует его заново, а
уже опубликованный rock вместо этого получает новую `--revision`. Rock с
нескольких машин, собранные в один каталог  -  например, из шагов матрицы
CI,  -  индексируются с помощью `tt package index DIR`, которая также
записывает индекс, хранящийся отдельно от rock, для rock на страницах
релизов; см. [Запись индекса](rock-servers.md#writing-an-index).

`--format tt,rock` упаковывает архив `.tt` и rock из одной сборки;
`--without-deps` и подпись относятся только к архиву.

`--format rock-src` упаковывает исходный rock, `<name>-<version>.src.rock`,
для платформы, под которую бинарный rock не опубликован: тот же rockspec и
файлы проекта, которые отслеживает git, включая файлы его сабмодулей, а также
файл `VERSION` с версией, поскольку у распакованного rock нет истории git, из
которой её можно вывести. Манифест и файлы лицензии упаковываются независимо
от того, отслеживает ли их git; отсутствие файла лицензии приводит к ошибке
упаковки, как и при упаковке бинарного rock; файл компонента, который git не
отслеживает и не игнорирует, исключается с предупреждением, поскольку в
бинарном rock он есть, а в сборке из исходного rock его не будет. Вне
репозитория git упаковываются все файлы проекта, кроме `_build/`, `.rocks/` и
`_runtime/`. Rock воспроизводим: у его записей нет прав доступа, кроме бита
исполнения, и нет собственного времени: каждая запись любого rock датирована
1980-01-01 00:00  -  самым ранним временем, поддерживаемым zip, которое
`unzip -l` показывает как есть в любом часовом поясе. Упаковка только
исходного rock ничего не собирает  -  ни хука, ни backend, ничего не
устанавливается в `.rocks/`,  -  поэтому ей не требуются ни компилятор, ни
заголовочные файлы Tarantool; манифест проверяется, а локфайл разрешается
или отклоняется при `--locked`, как это делает сборка.
`--format rock,rock-src` собирает один раз, для бинарного rock. Упаковка на
каждой платформе с `--format rock` и одна с `--format rock-src` в любом месте
наполняют сервер всеми rock версии.

Проект, который зависит от такого rock, собирает его из исходного rock, когда
на серверах, с которых он устанавливает rock, нет rock для его платформы  -
ни бинарного, ни `.all`: tt скачивает исходный rock в `_build/src/`, собирает
пакет внутри него по его манифесту, как собирает зависимость по пути, и
устанавливает в `.rocks/` в версии, зафиксированной в локфайле, включая
ревизию, а файлы лицензии пакета кладёт в `doc/`, как они лежат в его
бинарном rock; файл, которого нет в исходном rock (файл, не отслеживавшийся
git там, где rock упаковывали), вызывает предупреждение. Хуки пакета не
запускаются. Собранный так rock не собирается заново, пока дерево содержит его
в этой версии. Исходный rock не tt-пакета  -  без `app.manifest.toml`  -
приводит к ошибке сборки. Исходный rock собирает только tt: LuaRocks, включая
`tt rocks`, не находит в нём ничего для сборки (см.
[tt rocks](rock-servers.md#tt-rocks)).

Руководство [Publish a module as a rock](../how-to/rocks.md) проводит один
модуль через всё это: его манифест, его версии, его rock, сервер и индекс для
них, а также проект, который от него зависит.

## Установка {#installing}

`tt package install ARCHIVE` устанавливает пакет в один из
[scope](projects-and-scopes.md#scopes):

- **Проект** (по умолчанию): пакет становится гостем проекта. Его модули
  rocks добавляются в `.rocks/` проекта; когда два пакета фиксируют
  зависимость на разных версиях, установка выбирает версию, принимаемую
  обоими, или завершается ошибкой с объяснением причины. Проект, не имеющий
  собственного Tarantool, получает рантайм из архива.
- **Пользовательский или системный scope**: архив становится версией
  приложения, `<root>/versions/<name>/<name>_<version>/`, и ссылка
  `<root>/apps/<name>` указывает на неё. Его рантайм попадает в
  `<root>/versions/`, используется совместно, как бинарный файл,
  установленный через `tt binary`, и приложение работает на нём независимо
  от того, что выбрано в `<root>/bin/`. Версии сосуществуют рядом;
  `--upgrade` устанавливает только более новую версию, а `--force`
  переустанавливает уже имеющуюся, в чём отказывает, пока запущен инстанс
  приложения.

`tt package list` показывает содержимое scope; `tt package uninstall`
удаляет гостя из проекта или все версии приложения из пользовательского или
системного scope, сохраняя данные инстансов в `<root>/var/` и пару хоста в
`<root>/etc/<name>/`.

Архив с зависимостями устанавливается без доступа к сети. См.
[Install an application for a user](../how-to/user-scope.md) и
[Run instances under systemd](../how-to/systemd.md).
