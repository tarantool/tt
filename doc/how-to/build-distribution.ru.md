# Сборка дистрибутива tt

Модуль tt - это модуль Go, скомпилированный внутрь самого tt, а не
работающий рядом с ним: его пакет экспортирует конструктор
`func New(sdk.Services) []sdk.Mount`, возвращающий команды, которые он
добавляет (см. [Write a tt module](write-a-module.md) и
[SDK](https://github.com/tarantool/tt/blob/v3/sdk/README.md)). Дистрибутив
tt - это ядро tt и набор таких модулей, собранных в один бинарный файл и
описанных в `tt.manifest.toml`:

```toml
manifest_version = "0.1"
manifest_kind = "tt-distribution"

[package]
name = "tt"

[core]
tt = "v3.0.0-alpha.2"

[distribution]
title = "Tarantool CLI EE"
edition = "ee"
integrity = "rsa"

[dependencies]
aeon = "github.com/tarantool/tt/modules/aeon"
migrations = "./plugins/migrations"
foo = "github.com/acme/tt-foo@v1.2.0"
```

Обязательны только поля `manifest_version` и `manifest_kind`; все остальные
поля описаны в [tt.manifest.toml](../reference/tt-manifest.md). Без секции
`[core]` дистрибутив собирается на ядре того tt, который выполняет сборку;
`tt` принимает запрос версии Go для модуля ядра - версию, коммит или
`latest`, а `path` - локальный чекаут ядра. Версию или коммит надёжнее
фиксировать: Go читает `v3` как "самый новый релиз v3.x.y", а не как ветку
`v3`, и пока у tt 3 есть только предварительные версии, под этот запрос
ничего не подходит. Секция `[distribution]` задаёт представление бинарного
файла (`title`, `edition`), провайдер контроля целостности (`none` или
`rsa`), а также наличие собственных команд tt (`builtin`) и внешних модулей
(`external_modules`); по умолчанию включены и те, и другие. Секция `[build]`
задаёт реализацию TLS (`ssl`: `default`, `openssl` или `openssl_static`,
переопределяется переменной `TT_CLI_BUILD_SSL`), сборку с `cgo` (по
умолчанию только для сборок с OpenSSL), дополнительные теги сборки `tags` и
флаги линковщика `ldflags`.

Зависимость - это локальный каталог (`./...`, `../...` или абсолютный путь),
путь к модулю либо путь к модулю с версией после `@`; в полной форме это
таблица с полями `module`, `version`, `path`, `package` и `symbol`:
конструктором считается функция `New` в корневом пакете модуля, если
`package` и `symbol` не указывают иное. Модуль из репозитория ядра, такой как
`aeon`, собирается на коммите ядра; любой другой модуль без версии - на самой
свежей версии (`latest`).

```sh
tt binary build tt                  # собрать ./tt из ./tt.manifest.toml
tt binary build tt --update         # взять самые свежие версии ядра и модулей
tt binary build tt --locked -o tt   # собрать ровно то, что зафиксировано в lock-файле
```

Тулчейн Go должен быть в `PATH`. Сборка генерирует основной модуль,
требующий ядро и модули, компилирует его с теми же тегами сборки, с которыми
собран сам tt, запускает `tt version` для результата и записывает
`tt.manifest.lock` и `tt.manifest.sum` рядом с манифестом. Оба файла
фиксируют в репозитории: пока манифест остаётся прежним, следующая сборка
берёт версии из lock-файла, а флаг `--locked` завершается с ошибкой, если
lock-файл или модули Go расходятся. Lock-файл фиксирует то, из чего собирается
бинарный файл, а не параметры компиляции: реализацию TLS, теги и тулчейн Go
каждая сборка выбирает сама, поэтому один lock-файл подходит для любой из них,
а сборка, не фиксирующая ничего нового (например, выполненная другим tt),
оставляет оба файла без изменений.

У локального модуля, локального ядра или каталога из `[replace]` нет версии,
которую можно зафиксировать, поэтому lock-файл сохраняет `content_hash` -
хеш файлов по путям и содержимому, так же как Go вычисляет хеш модуля для
`go.sum`. Это те самые файлы, которые бандл копирует при `--vendor`: все
обычные файлы каталога, кроме каталогов VCS, каталогов `vendor`, вложенных
модулей и файлов, игнорируемых `.gitignore`. Файлы `.gitignore` учитываются
как собственный файл модуля, так и файлы в вышестоящих каталогах вплоть до
корня git-репозитория; вне репозитория - вплоть до каталога манифеста, если
модуль находится внутри него. Они читаются по правилам git, но без запуска
git, поэтому архив чекаута хешируется так же, как и сам чекаут; файлы
`.git/info/exclude` и настройка `core.excludesFile`, различающиеся от машины к
машине, не читаются, а отслеживаемый git файл, попадающий под `.gitignore`, не
учитывается. Файлы, из которых Go может собрать модуль, учитываются даже при
наличии их в правилах игнорирования: исходные файлы Go и cgo, `go.mod`,
`go.sum` и файлы, внедряемые через `//go:embed`. При изменении этих файлов
сборка с `--locked` завершается с ошибкой; обычная сборка фиксирует их заново.
Бинарный файл, собранный в чекауте ядра (например, `./tt`), изменением не
считается: `.gitignore` самого tt его игнорирует.

Команда `tt version` для собранного файла показывает версию дистрибутива и
ядра tt, на котором он собран; команда `tt version --modules` выводит список
модулей с версиями, зафиксированными Go для их модулей, или `(devel)` для
локального модуля:

```sh
$ ./tt version --modules
Tarantool CLI EE version 3.0.0, linux/amd64. commit: 1a2b3c4
Tarantool CLI core version 3.0.0. commit: 9031d7ad96d9 (v3.0.1-0.20261028190206-9031d7ad96d9)
  aeon        v0.0.0-20261028190206-9031d7ad96d9    github.com/tarantool/tt/modules/aeon
  builtin     v3.0.1-0.20261028190206-9031d7ad96d9  github.com/tarantool/tt/v3
  migrations  (devel)                               example.com/tt-ee/plugins/migrations
```

## Подмена модулей Go {#replacing-go-modules}

Модуль tt собирается с зависимостями, указанными в его собственном `go.mod`,
но Go применяет директивы `replace` только из главного модуля, поэтому
модуль, зависящий от неопубликованной библиотеки или библиотеки не той
версии, не может задать подмену сам. Секция `[replace]` добавляет подмену в
`go.mod`, генерируемый при сборке, перед запуском `go mod tidy`:

```toml
[replace]
"gitlab.corp.mail.ru/tarantool/go-migration" = "../go-migration"
"github.com/tarantool/go-storage/v2" = "github.com/tarantool/go-storage/v2@v2.1.0-rc1"
"github.com/acme/old@v1.2.3" = "github.com/acme/new@main"
```

Ключ - это путь к модулю Go, при необходимости с `@version` для подмены только
этой версии, как в `go.mod`. Значение - либо локальный каталог (начинается с
`./`, `../` или `/` и задаётся относительно манифеста), содержащий указанный
модуль, либо `module@version`, где версией может быть любой запрос (ветка,
коммит, `latest`); сборка разрешает его в точную версию, как и для модулей, а
lock-файл фиксирует её. Ядро, модули из его репозитория и модули tt из
`[dependencies]` здесь подменять нельзя, это считается ошибкой: для ядра
предусмотрены `[core].path` и флаг `--core`, а у модуля tt есть собственные
параметры `path` и `version`. Подмена, из которой не берётся ни один пакет
сборки, ни на что не влияет, и сборка выводит предупреждение о ней.

Lock-файл сохраняет каждую запись из `[replace]`: каталог - по значению
`content_hash`, вычисленному так же, как для локального модуля (см. выше), а
модуль - по его точной версии. Сборка с `--locked` завершается с ошибкой, если
подменённый каталог изменился, точно так же, как и для локального модуля. Флаг
`--vendor` копирует подменённые каталоги в `local/replace/` бандла, на который
`go.mod` перенаправляет их по относительному пути, поэтому бандл собирается в
автономном режиме.

## Сборка на другом ядре {#building-on-another-core}

Флаг `--core VALUE` или переменная окружения `TT_DIST_CORE` (флаг имеет
приоритет) собирают дистрибутив на ядре, отличном от указанного в `[core]`,
без правки манифеста: на локальном чекауте (существующий каталог или путь,
начинающийся с `./`, `../` или `/`, относительно каталога проекта) либо на
запросе версии в формате `[core].tt`. Это нужно для сборки дистрибутива с ещё
не выпущенными изменениями ядра, а также в CI самого tt, где дистрибутивы
собираются из рабочего дерева:

```sh
tt binary build tt --core ../tt
TT_DIST_CORE=. tt binary build tt --manifest dist/tt.manifest.toml
```

Такая сборка является сборкой для разработки (development build). Её ядро и
модули из репозитория ядра не берутся из lock-файла, а сам lock-файл и файл
контрольных сумм не записываются; остальные модули по-прежнему берутся из
lock-файла, пока манифест ему соответствует. Флаг `--locked` отклоняет такую
сборку.

## Автономная сборка {#offline-build}

Флаг `--vendor DIR` создаёт бандл вместо бинарного файла: всё необходимое
для сборки дистрибутива, из чего один лишь тулчейн Go собирает бинарный файл
на машине без сети, кэша модулей и установленного tt.

```sh
tt binary build tt --locked --vendor dist/bundle
```

Бандл содержит сгенерированные `go.mod`, `go.sum` и `main.go`, каталог
`vendor/` со всеми пакетами, из которых собирается бинарный файл (ядро, модули
из его репозитория, модули tt, сторонние модули и внедряемые ими файлы),
каталог `local/` с копией каждого локального модуля (локальное ядро,
зависимости по путям и каталоги из `[replace]`), на которые `go.mod`
перенаправляет их по относительному пути, а также параметры сборки:
`build.env` задаёт теги, флаги линковщика и cgo для каждой реализации TLS,
реализацию, с которой собирался бандл, тулчейн и версию, а скрипт `build.sh`
выполняет с ними сборку. Бандл не содержит путей к каталогам машины, на
которой он создавался, поэтому его можно переносить куда угодно; при создании
бандла однократно выполняется автономная сборка.

На автономной машине при наличии тулчейна Go, указанного в `build.env`
(`TT_DIST_TOOLCHAIN`), или более нового тулчейна в `PATH`:

```sh
sh bundle/build.sh                         # TLS, с которым собирался бандл
sh bundle/build.sh openssl_static ./tt     # либо default, openssl; и выходной файл
```

Скрипт `build.sh` представляет собой всего лишь:

```sh
cd bundle
. ./build.env
GOFLAGS=-mod=vendor GOPROXY=off GOWORK=off GOTOOLCHAIN=local \
CGO_ENABLED=$TT_DIST_CGO_DEFAULT \
    go build -trimpath -tags "$TT_DIST_TAGS_DEFAULT" \
        -ldflags "$TT_DIST_LDFLAGS_DEFAULT" -o tt .
```

Реализациям OpenSSL требуются компилятор C и заголовочные файлы OpenSSL на
автономной машине; на macOS скрипт `build.sh` использует
`TT_DIST_LDFLAGS_DARWIN_*`.
