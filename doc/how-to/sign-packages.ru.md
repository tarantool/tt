# Подпись пакетов

Дистрибутив, собранный с `integrity = "rsa"`, подписывает пакеты закрытым
ключом RSA и запускает их с проверкой по открытому ключу. Сам по себе tt
ничего не проверяет: в нём нет провайдера контроля целостности (см.
[Build a distribution of tt](build-distribution.md)).

## Создание ключей {#make-the-keys}

Ключи хранятся в формате PEM: закрытый - в PKCS#1 или PKCS#8, открытый -
в PKIX или PKCS#1, как их создаёт openssl:

```console
$ openssl genrsa -out private.pem 2048
$ openssl rsa -in private.pem -pubout -out public.pem
```

## Подпись архива {#sign-an-archive}

Команда `tt package pack --with-integrity-check private.pem` подписывает
собираемый архив. В корень пакета помещаются два файла с хешами, рядом с
каждым из которых лежит подпись RSASSA-PSS (`.sig`): `hashes.json` перечисляет
всё, что загружает Tarantool, - исходные тексты на Lua, разделяемые
библиотеки, кластерные конфигурации шаблонов и скрипты, запускаемые записями
инстансов, - а `env_hashes.json` содержит все остальные файлы пакета:
манифест, lock-файл, `VERSION`, описания инстансов, программы в `.rocks/bin/`.
Для каждой среды выполнения, которую архив включает в `_runtime/`,
создаётся собственный `env_hashes.json`, в котором перечислены её исполняемый
файл и заголовочные файлы tarantool по путям, куда их раскладывает
`tt package install`. Подписанный пакет запускает только собственные файлы:
если запись шаблона запускает скрипт или бинарный файл вне пакета либо
программу, которая не собирается в `.rocks/bin/`, сборка пакета завершается
с ошибкой. Точно так же отвергается запись инстанса Tarantool с `env` и
наличие каталога `var/` в корне пакета (см. ниже раскладку в Tarantool
Enterprise). Пакет нельзя подписать с флагом `--without-deps`, поскольку
при установке такого пакета скачиваются зависимости, которые никто не
подписывал.

## Установка подписанного архива {#install-a-signed-archive}

Команда `tt --integrity-check public.pem package install` устанавливает
только подписанный архив - в пользовательский или системный scope: версия
и каждая включённая среда выполнения проверяются перед размещением на месте
(их подписи, каждый перечисленный файл и то, что в списке учтены все файлы),
поэтому изменённый или добавленный файл отвергается. Среда выполнения, уже
установленная в этом месте через `tt binary` или при более ранней установке,
обязана быть подписанной: если у неё нет собственных файлов с хешами, она
получает файлы архива и проверяется по ним.

## Запуск с проверкой {#run-checked}

Команда `tt --integrity-check public.pem instance start` проверяет каждое
приложение в его собственном каталоге - в проекте или в установленной
версии - и в каталогах сред выполнения, на которых оно работает, независимо
от того, из какого каталога запущен tt, и запускает только то, что ими
подписано: tarantool приложения, который обязан быть подписанным tarantool из
архива, а не бинарным файлом из `PATH`, скрипт записи, бинарный файл
внешнего процесса, который ищется только в `.rocks/bin/` приложения, и сам
tt, запускающий watchdog, который обязан быть включённым в пакет.
Watchdog повторно проверяет их каждые `--integrity-check-period` секунд и
при ошибке проверки останавливает инстанс навсегда. Tarantool получает
`hashes.json` приложения для проверки того, что он загружает.

## Ограничения {#limits}

Пара хоста в `<root>/etc/<app>/` не входит в пакет, и приложение,
запускаемое по ней, при включённых проверках отвергается; оно запускается
по шаблону своего пакета, `--template`. Подписанная установка в scope
проекта, чей корень установки проект делит с гостевыми пакетами, и подпись
проекта в процессе разработки пока не поддерживаются. Подписи содержат
случайную соль, поэтому подписанный архив, в отличие от неподписанного, не
воспроизводится бит в бит.

С флагом `--integrity-check` tt читает манифесты и исполняемые файлы
[внешних модулей](external-modules.md#with-integrity-checks) также через
проверку, и файл, не перечисленный ни в одном подписанном файле с хешами,
отвергается: модуль вне подписанного дерева пропускается с предупреждением,
а модуль, чей исполняемый файл не подписан, не запускается.

## Раскладка каталогов в Tarantool Enterprise {#the-layout-on-tarantool-enterprise}

tt передаёт инстансу пути раскладки - каталоги данных, pid-файл, сокеты и
лог - через переменные `TT_*_DEFAULT` его окружения. Tarantool Enterprise при
проверке целостности запускается с пустым окружением, поэтому под
`--integrity-check` эти переменные до него не доходят, и он возвращается к
значениям по умолчанию Tarantool относительно своего рабочего каталога
(каталога установленной версии): `var/lib/<instance>` для данных,
`var/run/<instance>/tarantool.pid` и `var/run/<instance>/tarantool.control`,
а также `var/log/<instance>/tarantool.log` для файла лога.

Подписанная установка превращает эти значения по умолчанию в саму
раскладку. Команда `tt package install --integrity-check` создаёт в версии
`var/lib`, `var/run` и `var/log` как ссылки на `<root>/var/lib/<app>`,
`<root>/var/run/<app>` и `<root>/var/log/<app>`, поэтому конфигурация, не
указывающая пути явно, сохраняет данные, pid-файл и сокет консоли инстанса в
раскладке корня, где их находит tt, точно так же, как без проверок. Каждая
версия приложения ссылается на те же каталоги, поэтому данные переживают
обновление, а удаление версии удаляет её ссылки, но не сами данные.
Ссылки не входят в состав подписанного содержимого, и подписанный пакет не
может содержать собственный каталог `var/`: сборка пакета завершится с
ошибкой. `tt instance start --integrity-check` создаёт недостающие ссылки в
версии - установленной до того, как их стал делать tt, - если у неё есть
права на запись туда, и отказывается запускать инстанс, в версии которого
на этом месте находится что-то другое.

Конфигурация может по-прежнему задавать пути сама - в кластерной
конфигурации пакета или в его хранилище конфигураций; tt считывает каталоги
данных, сокет консоли и первый unix-сокет из `iproto.listen` из конфигурации
инстанса с подстановкой `{{ instance_name }}`, `{{ replicaset_name }}` и
`{{ group_name }}`. В системном scope, корнем которого в Linux служит
`/opt/tarantool`, для пакета `<app>`:

```yaml
snapshot:
  dir: /opt/tarantool/var/lib/<app>/{{ instance_name }}
wal:
  dir: /opt/tarantool/var/lib/<app>/{{ instance_name }}
vinyl:
  dir: /opt/tarantool/var/lib/<app>/{{ instance_name }}
quiver:
  dir: /opt/tarantool/var/lib/<app>/{{ instance_name }}
process:
  pid_file: /opt/tarantool/var/run/<app>/{{ instance_name }}/tarantool.pid
console:
  socket: /opt/tarantool/var/run/<app>/{{ instance_name }}/tarantool.control
iproto:
  listen:
  - uri: unix/:/opt/tarantool/var/run/<app>/{{ instance_name }}/tarantool.sock
```

Параметр `quiver.dir` есть только в Tarantool Enterprise; Tarantool Community
его отвергает. Перемещение путей по умолчанию через `process.work_dir`
невозможно: Tarantool ищет модули приложения, в том числе `app.file`, в своём
рабочем каталоге и после его переноса ничего там не находит.

То, что проверки отсекают вместе с окружением, остаётся недоступным, как
было и в tt 2:

- По умолчанию нет адреса iproto: инстанс слушает то, что указано в
  секции `iproto.listen` его конфигурации, и команде `tt connect --binary`
  нужен указанный там unix-сокет; `tt connect` через сокет консоли работает
  и без него.
- Лог выводится в стандартный поток ошибок инстанса, который tt записывает
  в `tt.log` раскладки, откуда его читает `tt instance logs`; директива
  `log.to: file` записывает `tarantool.log` рядом с ним.
- Переменная `env` из записи инстанса Tarantool до него не доходит: сборка
  подписанного пакета и `tt instance start --integrity-check` отвергают
  запись, задающую её, а значения должны находиться в конфигурации.
  Внешний процесс сохраняет свои переменные `env`: их запускает tt.
- Запись, запускающая собственный скрипт, при проверках отвергается: tt
  запускает её через лаунчер, берущий скрипт и пути инстанса из окружения.
  Вместо этого инстанс настраивается кластерной конфигурацией.
