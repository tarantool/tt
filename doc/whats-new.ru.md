# Что нового в tt 3 {#что-нового-в-tt-3}

tt 3 - это переработанный tt 2.x. Главные изменения:

- Приложение - это **пакет**: манифест описывает его зависимости, а
  локфайл фиксирует их точные версии.
- Приложение поставляется одним **архивом**, который устанавливается без
  доступа к сети.
- На хосте приложение работает из **пары файлов**, описывающих, какие
  инстансы здесь запускаются и как они настроены.

tt 3 поддерживает только Tarantool 3. При переходе с tt 2.x см.
[Переход с tt 2.x](migration_from_older_versions.md).

## Без конфигурационного файла {#без-конфигурационного-файла}

В tt 3 нет `tt.yaml`. Каталог, из которого запускается команда, определяет
объект её действия:

- Внутри [проекта](concepts/projects-and-scopes.md) tt ищет корень проекта
  вверх от текущего каталога. Поэтому команды работают из любого подкаталога
  проекта.
- Вне проекта область установки (scope) выбирается флагом:
  + `--scope user`: приложения и бинарные файлы для текущего пользователя;
  + `--scope system`: приложения и бинарные файлы для всего хоста.

  У каждого scope свой корневой каталог, но структура каталогов везде
  одинаковая.

## Приложения - это пакеты {#приложения---это-пакеты}

Пакет описывается двумя файлами в корне проекта:

- `app.manifest.toml` - манифест. Он объявляет имя пакета, совместимые
  версии Tarantool и tt, зависимости и зависимости для разработки,
  компоненты сборки и продукты для упаковки.
- `app.manifest.lock` - локфайл. Он фиксирует точные версии всех прямых и
  транзитивных зависимостей, поэтому сборки одного и того же коммита везде
  устанавливают одни и те же версии.

Например:

```sh
tt new
tt package add checks '>=3.0.0'
tt package build
tt test
```

- `tt new` создаёт заготовку манифеста.
- `tt package add`, `remove`, `update`, `resolve` и `deps` управляют
  зависимостями. Они редактируют манифест на месте и сохраняют комментарии
  в нём.
- Локфайл изменяется только по явному запросу. С `--locked` устаревший
  локфайл считается ошибкой, что полезно в CI.
- `tt package build` устанавливает зависимости в `.rocks/` и собирает
  компоненты:
  + модули на Lua;
  + нативные модули с помощью backend'ов `c`, `lua-c`, `cargo`, `zig`,
    `cmake`, `make` или `shell`. Нативный модуль может быть
    [написан на Rust](how-to/rust-modules.md) или
    [на Zig](how-to/zig-modules.md);
  + программы для внешних процессов с помощью backend'ов `go`, `cargo`,
    `zig`, `cmake`, `make` или `shell`; один компонент может собирать
    одновременно модуль и программу.
- Версия пакета берётся из `VERSION` или ближайшего тега git. В коде её
  можно прочитать через `require('<name>.version').version`.
- `tt run` запускает Tarantool проекта и передаёт аргументы без изменений.
- `tt test` собирает пакет и запускает его тесты с помощью luatest. Если
  luatest не объявлен в манифесте, tt устанавливает его автоматически.

См. [Пакеты](concepts/packages.md) и
[Первый пакет](get-started/first-package.md).

## Самодостаточные архивы {#самодостаточные-архивы}

`tt package pack` создаёт архив `<name>-<version>-<os>-<arch>.tt` в формате
tar.zst. Архив воспроизводим: один и тот же коммит даёт побайтно
идентичный архив.

По умолчанию архив включает всё, что нужно приложению: зависимости, шаблоны
инстансов, а также требуемые версии Tarantool, tt и TCM. Это позволяет
`tt package install` работать без доступа к сети.

```console
$ tt package pack
.../kv-api/_build/pack/kv-api-1.1.0-linux-amd64.tt
$ tt package install --scope system _build/pack/kv-api-1.1.0-linux-amd64.tt
```

При установке архива в user или system scope:

- Архив становится новой версией приложения, и `<root>/apps/<name>`
  атомарно переключается на неё.
- Каждое приложение работает на версии Tarantool, зафиксированной в его
  собственном локфайле. Приложения на разных версиях Tarantool могут
  работать бок о бок на одном хосте.
- `--upgrade` устанавливает более новую версию. Работающие инстансы
  сохраняют текущую версию до `tt instance restart`.
- Данные и конфигурация хоста хранятся отдельно от версий приложения,
  поэтому они переживают обновления и удаление.

При установке в проект архив становится гостевым пакетом, чьи rock'и
подключаются к проекту.

Дистрибутив tt, собранный с провайдером целостности,
[подписывает архивы](how-to/sign-packages.md) и запускает только
подписанные.

## Выбор rock-серверов {#выбор-rock-серверов}

tt берёт список rock-серверов из первого настроенного источника в таком
порядке:

1. Флаг `--registry`.
2. Переменная окружения `TT_REGISTRIES`.
3. Настройка `[platform].registries` в манифесте.
4. Встроенный список.

`tt registry list` показывает, какой список используется.

- Rock-сервер может быть URL-адресом HTTP(S) или локальным каталогом.
- `tt package search` ищет по всем настроенным серверам.
- `tt package download` скачивает rock'и в каталог, который сам может
  служить rock-сервером. Это позволяет подготовить зеркало для сборки в
  офлайне.
- `tt rocks` использует go-luarocks - движок LuaRocks, написанный на Go.

См. [Rock-серверы](concepts/rock-servers.md).

## Инстансы: одно описание, три вида {#инстансы-одно-описание-три-вида}

Приложение работает из пары файлов:

- `instances.yaml` описывает, какие инстансы запускаются на этом хосте;
- `config.yaml` содержит кластерную конфигурацию Tarantool 3.

Эти файлы находятся в `.templates/<name>/` проекта или установленной версии
приложения. Копии для конкретного хоста помещаются в `<root>/etc/<app>/`.

Например, `instances.yaml` может содержать:

```yaml
"*":                       # каждый инстанс топологии config.yaml
  restart: on-failure
legacy:
  script: init.lua         # приложение на box.cfg, как в tt 2.x
gateway:
  binary: ./bin/gateway    # внешний процесс, не Tarantool
  args: [--port, "8080"]
```

- tt запускает, останавливает, сообщает статус и собирает логи одинаково
  для трёх видов инстансов:
  + инстансов Tarantool из кластерной конфигурации;
  + [приложений на box.cfg](how-to/script-instances.md);
  + [внешних процессов](how-to/external-processes.md).
- Каждый инстанс работает под watchdog'ом tt. После сбоя tt перезапускает
  его в соответствии с политикой `restart`.
- `tt instance start --foreground` запускает все инстансы на переднем
  плане и выводит их поток вывода в stdout. Этот режим предназначен для
  контейнеров.
- Команды для инстансов сгруппированы в `tt instance`. Целями могут быть
  `APP:INSTANCE`, `APP:*` или список.
- `tt instance status --details` показывает, какую версию Tarantool
  использует инстанс и откуда она взята.
- `stop`, `restart`, `kill` и `clean` запрашивают подтверждение только в
  терминале. В скриптах передаётся `--yes`.
- `restart` проверяет, что все цели могут запуститься, перед остановкой
  любых инстансов.

См. [Инстансы](concepts/instances.md) и
[Кластер на ноутбуке](get-started/first-cluster.md).

## Юниты systemd из tt {#юниты-systemd-из-tt}

Для приложения, установленного в system scope, tt управляет юнитами systemd:

- `tt service systemd install <app>` создаёт шаблонный юнит приложения и
  drop-in для каждого инстанса.
- `tt service systemd generate` выводит юниты без их установки.
- `tt service systemd uninstall` удаляет юниты.

Команды `tt instance` распознают инстансы под управлением systemd и
направляют к `systemctl`.

См. [Запуск инстансов под systemd](how-to/systemd.md).

## Бинарные файлы для проекта, пользователя и хоста {#бинарные-файлы-для-проекта-пользователя-и-хоста}

`tt binary install`, `switch`, `list` и `uninstall` управляют версиями
Tarantool Community Edition, Tarantool Enterprise Edition, tt, TCM и
Enterprise SDK. Бинарные файлы могут быть установлены в scope проекта,
пользователя или системы.

- Tarantool Community Edition устанавливается готовым бинарным файлом на
  Linux с glibc. tt устанавливает его из релиза на GitHub с проверкой
  контрольных сумм релиза. На остальных платформах сборка выполняется из
  исходников.
- `--from-build` подключает собранный вручную Tarantool без копирования его
  файлов.
- Первая установка в проект создаёт `.env/activate.sh`. Этот скрипт
  добавляет бинарные файлы проекта в `PATH`.

См. [Управление бинарными файлами](how-to/binaries.md).

## Собственный tt {#собственный-tt}

tt состоит из ядра и набора модулей на Go. `tt binary build tt` собирает
пользовательский [дистрибутив](concepts/distributions.md) из
`tt.manifest.toml`:

- Дистрибутив включает ядро и модули разработчика, скомпилированные во
  время сборки.
- У него могут быть собственное имя и редакция.
- Локфайл фиксирует его состав, а бандл исходников vendoring'а позволяет
  собирать без доступа к сети.

Внешние модули загружаются из каталогов в `TT_CLI_MODULES_PATH`. Модуль с
тем же именем, что и команда tt, заменяет эту команду.

См. [Сборка дистрибутива tt](how-to/build-distribution.md) и
[Внешние модули](how-to/external-modules.md).

## Журналы без Tarantool {#журналы-без-tarantool}

`tt data cat` и `tt data play` заменяют `tt cat` и `tt play`. Они читают
файлы `.xlog`, `.snap` и `.vylog`, а также vinyl-файлы `.run` и `.index`.
Модули чтения написаны на Go, поэтому установка Tarantool на хосте не
требуется.

- Каталог данных читается в порядке восстановления Tarantool: сначала самый
  новый снимок, затем файлы `.xlog` в порядке vclock. Транзакции, уже
  вошедшие в снимок, пропускаются.
- Изменения можно отфильтровать:
  + по vclock с помощью `--from-vclock` и `--to-vclock`;
  + по LSN одной реплики с помощью `--from` и `--to`.

  Обе границы включаются. Транзакция никогда не разбивается.
- `tt data cat -o json` выводит один JSON-объект на строку для использования
  в скриптах.
- `tt data play` применяет транзакции целиком там, где цель это
  поддерживает. Целью может быть `APP:INSTANCE` или URI. Команда
  поддерживает `--dry-run` и `--on-error`.

См. [`tt data`](reference/commands/data.md).

## Сделано для скриптов {#сделано-для-скриптов}

- Команды используют единообразные коды возврата; см. `tt help errors` для
  подробностей:
  + `1`: ошибка, которую пользователь может исправить;
  + `2`: сбой системы, где выполнялась команда;
  + `3`: частичный успех.
- `--log-format json` записывает один JSON-объект на каждую запись журнала.
  Учётные данные в URI маскируются в записях журнала.
- Журналы и индикатор выполнения выводятся в stderr, оставляя stdout для
  результатов команд.
- `tt instance status`, `tt registry list` и команды `tt package`,
  выводящие таблицы, поддерживают `-o json` и `-o yaml`.

## Установка одной строкой {#установка-одной-строкой}

Чтобы установить свежий релиз tt 3 на Linux или macOS с процессором Apple,
выполните:

```sh
curl -fsSL https://raw.githubusercontent.com/tarantool/tt/v3/install.sh | sh
```

См. [Установка](get-started/install.md).
