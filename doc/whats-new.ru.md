# Что нового в tt 3

tt 3 переосмысляет tt 2.x вокруг трёх идей: приложение - это **пакет** с
манифестом и локфайлом; оно поставляется единым **архивом**, который
ставится без сети; а на хосте запускается по **паре** файлов, описывающих,
что именно здесь работает. tt 3 поддерживает только Tarantool 3. Для перехода
с tt 2.x читайте [Переход с tt 2.x](migration_from_older_versions.md).

## Никаких конфигурационных файлов {#no-configuration-file}

У tt нет `tt.yaml`. Над чем именно выполняется команда, определяется местом
её запуска: tt ищет [проект](concepts/projects-and-scopes.md) от текущего
каталога вверх по дереву, поэтому любая команда работает из любого его
подкаталога. Вне проекта флаги `--scope user` и `--scope system` выбирают
приложения и бинарные файлы текущего пользователя или всей системы - у
каждого scope свой корневой каталог и общая для всех раскладка.

## Приложения - это пакеты {#applications-are-packages}

`app.manifest.toml` объявляет пакет: имя, версии Tarantool и tt, на которых
он работает, обычные и dev-зависимости, компоненты, из которых он собирается,
и продукты, в которые упаковывается. `app.manifest.lock` рядом фиксирует
каждую зависимость, прямую и транзитивную, чтобы сборка одного и того же
коммита везде ставила одинаковые версии.

```console
$ tt new
$ tt package add checks '>=3.0.0'
$ tt package build
$ tt test
```

- `tt new` создаёт скелет манифеста; `tt package add`, `remove`, `update`,
  `resolve` и `deps` управляют зависимостями, меняя манифест на месте и
  сохраняя комментарии. Локфайл обновляется только по явной команде, а с флагом
  `--locked` устаревший локфайл считается ошибкой, как и требуется в CI.
- `tt package build` ставит зависимости в `.rocks/` и собирает компоненты:
  модули Lua, нативные модули с бэкендами `c`, `lua-c`, `cargo`, `make` или
  `shell`, а также программы для внешних процессов с бэкендами `go` или
  `cargo`. Нативный модуль можно [написать на Rust](how-to/rust-modules.md).
- Версия пакета берётся из `VERSION` или ближайшего тега git, а код читает её
  через `require('<name>.version').version`.
- `tt run` запускает Tarantool проекта с переданными аргументами без
  изменений; `tt test` собирает пакет и прогоняет luatest по его тестам,
  устанавливая luatest сам, если тот не объявлен в манифесте.

См. разделы [Пакеты](concepts/packages.md) и
[Первый пакет](get-started/first-package.md).

## Самодостаточные архивы {#self-contained-archives}

`tt package pack` собирает `<name>-<version>-<os>-<arch>.tt`,
воспроизводимый архив tar.zst: один и тот же коммит упаковывается байт в
байт. По умолчанию архив содержит всё необходимое приложению - зависимости,
шаблоны инстансов, а также Tarantool, tt и TCM, на которых оно работает,
поэтому для `tt package install` сеть не нужна.

```console
$ tt package pack
$ tt package install --scope system kv-api-1.1.0-linux-amd64.tt
```

При установке в пользовательский или системный scope архив становится версией
приложения, и `<root>/apps/<name>` атомарно переключается на неё. Каждое
приложение работает на том Tarantool, который указан в его собственном
локфайле, поэтому приложения на разных версиях Tarantool спокойно уживаются
рядом. `--upgrade` ставит более новую версию, работающий инстанс остаётся на
своей версии до `tt instance restart`, а данные и конфигурация хоста лежат
отдельно от версий, переживая и обновление, и удаление. При установке в проект
архив становится гостевым пакетом, чьи rock-модули подключаются к проекту.

Дистрибутив, собранный с провайдером целостности,
[подписывает архивы](how-to/sign-packages.md) и запускает только подписанные.

## Rock-серверы на выбор {#rock-servers-you-choose}

Rock-серверы берутся из `--registry`, `TT_REGISTRIES`, `[platform].registries`
манифеста или встроенного списка - берётся первый заданный; `tt registry list`
показывает, какой именно. Сервером может быть URL по HTTP(S) или локальный
каталог. `tt package search` ищет по всем серверам сразу, а
`tt package download` собирает каталог rock-модулей, который сам служит
rock-сервером: готовое зеркало для офлайн-сборки. `tt rocks` работает на
go-luarocks - движке LuaRocks на Go.
См. [Rock-серверы](concepts/rock-servers.md).

## Инстансы: одно описание, три вида {#instances-one-description-three-kinds}

Приложение запускается по паре файлов: `instances.yaml` задаёт, что работает
на этом хосте, а `config.yaml` - кластерную конфигурацию Tarantool 3. Эта
пара лежит в `.templates/<name>/` проекта или установленной версии, либо в
`<root>/etc/<app>/` для конкретного хоста.

```yaml
"*":                       # каждый инстанс из топологии config.yaml
  restart: on-failure
legacy:
  script: init.lua         # приложение на box.cfg, как в tt 2.x
gateway:
  binary: ./bin/gateway    # сторонний процесс, не Tarantool
  args: [--port, "8080"]
```

- Наряду с инстансами Tarantool из кластерной конфигурации,
  [приложения на box.cfg](how-to/script-instances.md) и
  [внешние процессы](how-to/external-processes.md) запускаются,
  останавливаются, показывают статус и пишут логи одинаково.
- Каждый инстанс работает под watchdog'ом tt, который перезапускает его после
  падения, как указано в `restart`. `tt instance start --foreground` держит
  все инстансы на переднем плане и выводит их логи в stdout - специально для
  контейнеров.
- Команды собраны в `tt instance` и принимают цели вида `APP:INSTANCE`,
  `APP:*` или списком. `tt instance status --details` показывает, на каком
  Tarantool работает инстанс и откуда он взят.
- `stop`, `restart`, `kill` и `clean` запрашивают подтверждение только в
  терминале; скрипты передают `--yes`. `restart` проверяет готовность к
  запуску всех целей до того, как остановит хоть одну.

См. разделы [Инстансы](concepts/instances.md) и
[Кластер на ноутбуке](get-started/first-cluster.md).

## Юниты systemd прямо из tt {#systemd-units-from-tt}

`tt service systemd install <app>` создаёт шаблонный юнит для приложения,
установленного в системный scope, и drop-in для каждого его инстанса;
`generate` выводит их текст, а `uninstall` удаляет. Команды управления
инстансами понимают, какие инстансы запущены под юнитом, и в таких случаях
перенаправляют к `systemctl`. См.
[Запуск инстансов под systemd](how-to/systemd.md).

## Бинарные файлы для проекта, пользователя и хоста {#binaries-per-project-per-user-per-host}

`tt binary install`, `switch`, `list` и `uninstall` управляют Tarantool
Community и Enterprise, tt, TCM и Enterprise SDK в scope проекта, пользователя
или системы.

- Tarantool Community ставится в виде готового бинарного файла на Linux с
  glibc, а tt - из релиза на GitHub с проверкой контрольных сумм релиза; на
  остальных платформах выполняется сборка из исходников.
- `--from-build` привязывает собранный вручную Tarantool без копирования.
- При первой установке в проект создаётся `.env/activate.sh`, добавляющий
  бинарные файлы проекта в `PATH`.

См. раздел [Управление бинарными файлами](how-to/binaries.md).

## Свой собственный tt {#your-own-tt}

tt состоит из ядра и набора модулей на Go. `tt binary build tt` собирает
[дистрибутив](concepts/distributions.md) по `tt.manifest.toml`: ядро со
встроенными модулями под собственным именем и редакцией, зафиксированное
локфайлом и собираемое офлайн из вендоренного бандла. Внешние модули
подхватываются из `TT_CLI_MODULES_PATH`, причём модуль с именем команды tt
замещает её. См. разделы
[Сборка дистрибутива tt](how-to/build-distribution.md) и
[Внешние модули](how-to/external-modules.md).

## Журналы без Tarantool {#journals-without-tarantool}

`tt data cat` и `tt data play`, заменившие `tt cat` и `tt play`, читают
файлы `.xlog`, `.snap` и `.vylog`, а также файлы `.run` и `.index` движка
vinyl средствами Go: Tarantool на хосте не требуется ни одной из них.

- Каталог читается точно так же, как Tarantool восстанавливает данные:
  сначала самый свежий снапшот, затем xlog-файлы по порядку vclock, без
  транзакций, уже вошедших в снапшот.
- `--from-vclock` и `--to-vclock` отбирают изменения по vclock, а `--from` и
  `--to` - по LSN одной реплики, включая обе границы; транзакция никогда не
  разрывается пополам.
- `tt data cat -o json` выводит по одному объекту JSON на строку для удобной
  обработки в скриптах.
- `tt data play` применяет транзакции целиком, если целевая система это
  поддерживает, принимает как `APP:INSTANCE`, так и URI, и поддерживает флаги
  `--dry-run` и `--on-error`.

См. [`tt data`](reference/commands/data.md).

## Заточен под скрипты {#made-for-scripts}

- Коды возврата единообразны для всех команд: 1 - для ошибок, исправимых
  пользователем, 2 - для сбоев системы, в которой выполнялась команда, 3 - для
  частичного успеха. Они описаны в `tt help errors`.
- `--log-format json` пишет лог в виде отдельных объектов JSON на запись;
  учётные данные в URI маскируются в каждой записи лога.
- Лог и спиннер выводятся в stderr, поэтому stdout содержит только результат.
  `tt instance status`, `tt registry list` и команды `tt package`, выводящие
  таблицы, поддерживают флаги `-o json` и `-o yaml`.

## Установка одной строкой {#install-in-one-line}

```console
$ curl -fsSL https://raw.githubusercontent.com/tarantool/tt/v3/install.sh | sh
```

ставит самый свежий релиз tt 3 на Linux и на macOS с процессорами Apple.
См. [Установка](get-started/install.md).
