# app.manifest.toml

Манифест [пакета](../concepts/packages.md) в корне его проекта. `tt new`
создаёт его заготовку.

```toml
manifest_version = "0.1"

[package]
name = "kv-api"
description = "A key-value API"
include = ["init.lua"]

[platform]
tarantool = ">=3.0.0,<4.0.0"
tt = ">=3.0.0"
registries = ["https://rocks.tarantool.org/", "./vendor-rocks"]

[dependencies]
checks = ">=3.0.0"
mylib = { source = "path", path = "../mylib" }

[dev_dependencies]
luatest = "*"

[components.app]
path = "kv"

[components.native]
path = "native"
[components.native.build]
backend = "lua-c"
module = "fast_hash"
sources = ["fast_hash.c"]

[products.default]
components = ["app", "native"]
default = true

[hooks.pre_build]
backend = "shell"
command = "./gen.sh"
```

Неизвестное поле считается ошибкой, если только в манифесте не объявлена более
новая минорная версия `manifest_version`, чем известна tt,  -  в этом случае
выводится предупреждение. Более новая мажорная версия отвергается.

## Верхний уровень {#top-level}

| Поле | Обязательно | |
| --- | --- | --- |
| `manifest_version` | да | версия формата: `"0.1"` |
| `manifest_kind` | нет | `"app"` по умолчанию; у дистрибутива tt свой манифест, `tt.manifest.toml` |

## `[package]` {#package}

| Поле | Обязательно | |
| --- | --- | --- |
| `name` | да | строчные буквы, цифры и дефисы, имя начинается с буквы; не `bin` и не `manifests` |
| `description` | нет | одна строка, отображается командой `tt package list` |
| `license` | нет | |
| `license_files` | нет | файлы, включаемые в пакет: в корень архива и в `doc/` рока, который упаковывает `--format rock`, по их путям в проекте |
| `authors` | нет | |
| `repository` | нет | |
| `include` | нет | файлы проекта, помещаемые в корень архива |
| `generate_version_lua` | нет | `false` исключает `version.lua` из сборки; по умолчанию `true` |

## `[platform]` {#platform}

| Поле | Обязательно | |
| --- | --- | --- |
| `tarantool` | да | версии Tarantool с редакцией: `">=3.0.0"` или `">=3.0.0[ce]"` для Community, `">=3.3.0[ee]"` для Enterprise |
| `tt` | да | версии tt |
| `tcm` | нет | версии TCM, включаемые в архив; без редакции |
| `platforms` | нет | платформы, для которых предназначен пакет: `linux-amd64`, `linux-arm64`, `darwin-amd64`, `darwin-arm64` или только `any` |
| `registries` | нет | rock-серверы в порядке обращения вместо серверов по умолчанию: URL HTTP(S) или каталоги, относительно манифеста или абсолютные. См. [Rock-серверы](../concepts/rock-servers.md) |

Ограничение версии  -  список сравнений через запятую, например
`">=3.0.0,<4.0.0"`.

Рок, который зависит от `tarantool`, проверяется по `tarantool`: такого рока
нет ни на одном сервере. Если ни одна из этих версий ему не подходит,
резолв падает; если не подходит самая младшая, tt предупреждает, что нижнюю
границу стоит поднять. В локфайл для него ничего не попадает.

## `[dependencies]` и `[dev_dependencies]` {#dependencies-and-dev_dependencies}

Зависимость  -  rock в краткой форме:

```toml
checks = ">=3.0.0"           # ограничение; "*" для любой версии
```

или в полной форме:

| Поле | |
| --- | --- |
| `source` | `"registry"` (по умолчанию) или `"path"` |
| `version` | ограничение версии; обязательно для `registry` |
| `path` | каталог с rock относительно манифеста или абсолютный путь к нему; обязателен для `path`. См. [Зависимости из каталога](#path-dependencies) |
| `registry` | rock-сервер, откуда брать этот rock: URL http(s) или каталог, относительно манифеста или абсолютный |

Rock с указанным `registry` разрешается и устанавливается только с этого
сервера; зависимости этого rock берутся из реестров проекта.

Зависимости из `[dev_dependencies]` устанавливаются для тестов и инструментов
проекта и не включаются в пакет. Компонент может объявлять собственные
зависимости в `[components.<name>.dependencies]`.

### Зависимости из каталога {#path-dependencies}

Зависимость с `source = "path"` собирается из своего каталога, а как
именно  -  определяет то, что в нём лежит:

- `app.manifest.toml`: каталог  -  это отдельный проект, и tt собирает его
  так же, как `tt package build` собирает пакет,  -  компоненты продукта по
  умолчанию, их раскладку и `version.lua`,  -  а затем устанавливает в
  `.rocks/` как rock его пакета. Зависимость называется так же, как этот
  пакет, или как `rock` другого его продукта, и тогда собирается этот
  продукт. Её версия определяется в её каталоге так же, как версия пакета, а
  её зависимости  -  зависимости её продукта по умолчанию, которые разрешаются
  вместе с зависимостями проекта: относительный путь зависимости `path`
  берётся относительно самой зависимости, а у зависимости с `registry`
  остаётся её сервер. Её `[dev_dependencies]` и локфайл не используются;
  её хуки не запускаются, а rockspec рядом с манифестом игнорируется  -  о
  том и другом предупреждает разрешение локфайла проекта.
- `*.rockspec`: tt собирает описанный в нём rock.
- ни того, ни другого: собирать и устанавливать нечего, и локфайл только
  фиксирует каталог, без версии; в зависимостях rock проекта её нет.

Локфайл фиксирует зависимость из каталога по её пути, относительному от
проекта или абсолютному, как его записал манифест, и по хешу её файлов.
Абсолютный путь привязывает локфайл к машине: он верен только там, где
каталог лежит по этому пути. В хеш зависимости с манифестом не входят
`.git/`, `_build/`, `.rocks/`, `_runtime/`, её `app.manifest.lock` и то,
что игнорируют её файлы `.gitignore`, поэтому ни её собственная сборка, ни
сборка проекта не делают локфайл устаревшим; новая версия зависимости  -
делает, даже если её создали только коммит или тег. Зависимость в
подкаталоге репозитория, в том числе репозитория самого проекта, получает
версию только по своему каталогу
(см. [Сборка](../concepts/packages.md#building)): коммит или изменение в
другом месте репозитория её версию не сдвигает. tt собирает такую
зависимость в `_build/path/<name>/` проекта - там её stage, `TT_BUILD_DIR`
её компонентов и её `CARGO_TARGET_DIR` - и не трогает её каталог  -  кроме
того, что туда сами пишут её бэкенды сборки.

```toml
[dependencies]
memcached-contrib = { source = "path", path = "../memcached-contrib" }
```

## `[components.NAME]` {#componentsname}

| Поле | |
| --- | --- |
| `path` | каталог компонента относительно манифеста; обязателен |
| `kind` | `"module"` (по умолчанию) или `"executable"` |
| `include`, `exclude` | файлы компонента-модуля; по умолчанию `*.lua` и `*.so` |
| `namespace` | куда помещается компонент-модуль в `.rocks/share/tarantool/`: по умолчанию имя пакета, `""` для верхнего уровня |
| `dependencies` | зависимости компонента |
| `build` | сборка компонента, см. ниже; обязательна для исполняемого компонента |

Файл `.wasm`, раскладываемый компонентом-модулем, должен быть двоичным файлом
WebAssembly: файл другого типа приводит к ошибке сборки, а core-модуль,
который tarantool-wasm не загружает, раскладывается с предупреждением. `tt wasm
new` объявляет компоненты, собираемые tarawasm; см.
[Запуск компонентов WebAssembly](../how-to/wasm-components.md).

### `[components.NAME.build]` {#componentsnamebuild}

| Поле | Backend'ы | |
| --- | --- | --- |
| `backend` | | `c`, `lua-c` (компоненты-модули); `go` (исполняемые компоненты); `cargo`, `cmake`, `make`, `shell` (и те, и другие) |
| `cwd`, `env`, `output` | все | каталог запуска сборки, её окружение, создаваемые файлы |
| `incremental` | `make`, `shell` | `true` пропускает сборку, если входные данные те же, что при прошлой сборке, и её результаты ещё на месте |
| `make_target`, `entrypoint`, `flags` | `make` | `make_target` обязателен |
| `command`, `args` | `shell` | `command` обязателен |
| `module`, `sources`, `include_dirs`, `libraries`, `library_dirs`, `defines` | `c`, `lua-c` | `module` и `sources` обязательны |
| `module` | `cargo` | имя модуля, собираемого компонентом-модулем: по умолчанию имя библиотеки |
| `platforms.<os>` | `c`, `lua-c` | дополнительные `include_dirs`, `libraries`, `library_dirs`, `defines` для одной ОС |
| `package` | `go`, `cargo` | пакет Go (по умолчанию `.`) или пакет cargo |
| `static` | все | `true`: результату сборки ничего не нужно от машины, на которую он устанавливается, и сборка это проверяет; см. ниже |
| `name`, `tags`, `ldflags`, `cgo` | `go` | по умолчанию `name`  -  имя компонента; cgo по умолчанию выключен |
| `bin`, `features`, `profile` | `cargo` | для исполняемого компонента `bin` по умолчанию  -  имя компонента; `profile` по умолчанию `release` |
| `variables`, `targets`, `build_type` | `cmake` | `-D<name>=<value>` конфигурации, собираемые цели (по умолчанию все) и `CMAKE_BUILD_TYPE` (по умолчанию `RelWithDebInfo`); `output` обязателен |

Сборка получает свой контракт через окружение: `TT_OUTPUT_DIR`, куда
помещаются результаты сборки, `TT_PROJECT_ROOT`, `TT_PACKAGE`,
`TT_COMPONENT_NAME`, `TT_VERSION`, `TT_PLATFORM_OS` и `TT_PLATFORM_ARCH`.
Если tt знает Tarantool, для которого идёт сборка, она получает также
`TT_TARANTOOL_PREFIX`  -  префикс установки этого Tarantool  -  и
`TT_TARANTOOL_INCLUDE_DIR`  -  каталог его `module.h` и `lua.h`,
`<prefix>/include/tarantool`, с которым компилируют backend'ы `c` и `lua-c`;
то, чего tt не знает, не задаётся. `env` сборки не может переопределить их.
Если tt не находит Tarantool вовсе, компонент `c` или `lua-c` приводит к
ошибке сборки ещё до её начала: заголовочных файлов нет.

`TT_BUILD_DIR` - собственный каталог сборки для того, что она создаёт по
пути, вне исходников: объектных файлов, дерева сборки. Это
`_build/component/<component>/`; он существует к началу сборки и
сохраняется между сборками, так что сборка `make` пересобирает только
изменившееся; `--rebuild` сначала очищает его. Сборка `make` или `shell`,
которая пишет туда, а не рядом с исходниками, не трогает каталог
компонента, в том числе каталог path-зависимости - другой рабочей копии.

`cmake` собирает CMake-проект из `cwd`, где лежит его `CMakeLists.txt`, вне
исходников, в `TT_BUILD_DIR`:

```console
cmake -S <cwd> -B _build/component/<component> -DCMAKE_BUILD_TYPE=<build_type> \
    -D<name>=<value>... -DCMAKE_PREFIX_PATH=<префикс Tarantool>
cmake --build _build/component/<component> --config <build_type> --parallel <CPU> \
    --target <targets>...
```

и копирует файлы из `output`, пути которых указываются относительно дерева
сборки, в `TT_OUTPUT_DIR`; если сборка не создала какой-то из них, она
завершается ошибкой. Префикс Tarantool добавляется в `CMAKE_PREFIX_PATH` после
префиксов, заданных в `variables`, поэтому `find_path(... tarantool/module.h)`
обычного `FindTarantool.cmake` находит его заголовки. Дерево сборки
сохраняется между сборками, и cmake пересобирает в нём только изменившееся;
`--rebuild` конфигурирует новое дерево, как и сборка перемещённого проекта.
`CMAKE_BUILD_PARALLEL_LEVEL`, если задана, определяет число заданий, а
`CMAKE_GENERATOR` в `env` выбирает другой генератор. На macOS `.so`
компонента-модуля копируется как `.dylib`: там Tarantool загружает такие
файлы. Исполняемый компонент перечисляет свои программы в `output`. В `PATH`
должен быть CMake 3.15 или новее.

```toml
[components.memcached]
path = "memcached"
include = ["init.lua"]
[components.memcached.build]
backend = "cmake"
cwd = "."
variables = { ENABLE_BUNDLED_SMALL = "ON" }
targets = ["internalso"]
output = ["memcached/internal.so"]
```

`cargo` собирает бинарный файл `bin` исполняемого компонента и библиотеку
пакета для компонента-модуля: `cdylib`, то есть нативный модуль `<module>.so`
(`<module>.dylib` на macOS). Сборка получает `CARGO_TARGET_DIR` -
`_build/cargo/`, общий для cargo-компонентов проекта, как `target/` общий для
пакетов workspace: то, от чего они зависят, компилируется один раз.
`target-dir` из конфигурации cargo ему уступает, а `CARGO_TARGET_DIR` или
`CARGO_BUILD_TARGET_DIR` из `env` или из окружения, в котором работает tt,
сохраняются. Библиотека и бинарный файл берутся оттуда, где, по сообщениям
cargo, он их собрал. `--rebuild` запускает cargo, как и любая сборка, и cargo
пересобирает изменившееся, в том числе после смены компилятора. Каталог
`target/` компонента, собираемого cargo, не раскладывается. См.
[Сборка модуля на Rust](../how-to/rust-modules.md).

`static = true` требует, чтобы результату сборки ничего не было нужно от
машины, на которую устанавливается пакет, и сборка это проверяет: файл,
которому нужно больше, приводит к ошибке сборки с кодом выхода 2, а в
сообщении названы файл и то, что ему нужно.

- Программе исполняемого компонента не нужны ни загрузчик, ни разделяемые
  библиотеки. `go` и `cargo` собирают такую программу сами, только для
  Linux; то, что собирают `cmake`, `make` и `shell`, только проверяется.
- Модулю не нужны разделяемые библиотеки, кроме библиотеки C, которую
  Tarantool, загружающий модуль, уже загрузил сам: на Linux это `libc.so.6`,
  `libm.so.6`, `libdl.so.2`, `libpthread.so.0`, `librt.so.1`, загрузчик -
  `ld-linux-*` или, у musl, `ld-musl-*` и `libc.musl-*` - и `libgcc_s.so.1`,
  среда выполнения GCC, нужная любой сборке Tarantool; на macOS -
  `/usr/lib/libSystem.B.dylib`, причём для каждого среза универсального
  файла. Проверяются нативные файлы, которые сборка записывает в
  `TT_OUTPUT_DIR`, и файлы компонента, которые забирает раскладка. От
  backend'а ничего не требуется: нужную модулю библиотеку, например
  `libsasl2.so.2`, линкуют статически, из её `.a`, или загружают во время
  работы через `dlopen`. Модуль на C++ линкует `libstdc++` статически
  (`-static-libstdc++`); на macOS ему нужна `libc++`, которой в этом списке
  нет. Модуль, которому нужна более новая glibc, чем Tarantool, для которого
  он собирается, собирается с предупреждением: он не загрузится там, где
  этот Tarantool работает на более старой glibc.

Входные данные `incremental`-сборки  -  её блок сборки и файлы компонента,
кроме скрытых файлов, `_build/`, `_runtime/` и того, что игнорируют файлы
`.gitignore` проекта и компонента: то, что сборка генерирует, а git не
хранит, входными данными не является. Хеш входных данных её последней сборки
находится в `_build/cache/<component>.json`, а флаг `--rebuild` команд
`tt package build` и `tt package pack` запускает сборку в любом случае; см.
[Инкрементальные сборки](../concepts/packages.md#incremental-builds).

Каталог `.tarantool/bin` проекта, куда `tt binary` и `tt wasm prepare`
помещают программы проекта, идёт первым в `PATH` сборки и hook'а: в `command`
такая программа указывается без предварительного выполнения
`.env/activate.sh`.

`tt -V package build` перед запуском каждой команды сборки или hook'а
выводит в лог эту команду и каталог, в котором она запускается, и
показывает то, что команда печатает; без `-V` это показывается вместе с
командой, только если она завершилась ошибкой.

## `[products.NAME]` {#productsname}

| Поле | |
| --- | --- |
| `components` | компоненты продукта; обязательно |
| `default` | `true` задаёт продукт, который `build` и `pack` берут без `--product`; продукт по умолчанию ровно один |
| `rock` | имя рока, которым выпускается продукт, `[a-z][a-z0-9-]*`; по умолчанию у продукта по умолчанию - имя пакета, у другого - никакого |

В манифесте без `[products]` есть один продукт, `default`, состоящий из всех
компонентов.

Пакет из нескольких роков, например модуль и его инструменты, задаёт каждому
продукту, от которого зависят другие проекты, свой `rock`. Два продукта,
выпускаемые двумя роками, не делят компонентов: в дереве, где стоят оба
рока, их файлы оказались бы дважды. `version.lua` такого продукта лежит
под именем его рока, `<rock>/version.lua`, а не пакета. `tt package pack
--format rock --product NAME` упаковывает продукт в его рок; продукт без
рока упаковать нельзя. Path-зависимость - это продукт пакета из её
каталога: по умолчанию по имени пакета, другой - по его року.

## `[hooks.pre_build]` и `[hooks.post_build]` {#hookspre_build-and-hookspost_build}

Команда, запускаемая до или после сборки компонентов, с backend'ом `shell`
(по умолчанию) или `make` и полями сборки. Hook получает окружение сборки без
`TT_OUTPUT_DIR`, `TT_COMPONENT_NAME` и `TT_BUILD_DIR`.
